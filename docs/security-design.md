# Архитектура и механизмы безопасности

Этот документ описывает фактическую реализацию текущей версии проекта АСУ ТП «Автоматика». Он предназначен для понимания того, где именно находятся проверки доступа и как Python-клиент взаимодействует с PostgreSQL.

## 1. Общая схема

Приложение состоит из двух уровней:

```text
Пользователь
    │
    ▼
Python / Tkinter
    │
    │ psycopg2
    ▼
PostgreSQL: asu_tp_db
    │
    ├── LOGIN-роли user_*
    ├── групповые роли app_*
    ├── схема asu_schema
    ├── функции SECURITY DEFINER
    ├── матрица permissions / role_permissions
    ├── технологические объекты
    ├── access_log
    └── alarm_log
```

Python-клиент не подключается к БД под `postgres`. Введенный в окне логин нормализуется в `db_connection.py`: если префикса `user_` нет, он добавляется автоматически.

## 2. Идентификация и аутентификация

Аутентификацию выполняет сам PostgreSQL. Клиент передает в `psycopg2.connect()`:

- адрес и порт сервера;
- имя БД;
- LOGIN-роль вида `user_operator`;
- пароль, введенный пользователем;
- `sslmode` и тайм-аут из `config.py`.

После успешного соединения `f_get_my_role()` определяет запись пользователя в прикладной таблице `users` и возвращает его ФИО и роль.

Успешный вход отдельно фиксируется функцией `f_log_login()`, а выход — `f_log_logout()`.

Лимит неуспешных попыток (`MAX_LOGIN_ATTEMPTS`) реализован в `LoginWindow` и действует только в пределах текущего запуска окна авторизации. Это клиентское ограничение, а не серверная блокировка учетной записи.

## 3. Два слоя ролевой модели

### 3.1. PostgreSQL-роли

В `01_schema.sql` создаются групповые NOLOGIN-роли:

```text
app_unprivileged
app_operator
app_privileged
app_engineer
app_admin
app_ib_admin
```

`02_accounts.sql` создает LOGIN-роли:

```text
user_unprivileged
user_operator
user_privileged
user_engineer
user_admin
user_ib_admin
```

Каждая LOGIN-роль получает соответствующую групповую роль `app_*`.

### 3.2. Прикладная матрица

Внутри `asu_schema` существуют таблицы:

- `roles` — роли приложения;
- `permissions` — отдельные разрешения;
- `role_permissions` — связи «роль → разрешение»;
- `users` — прикладные учетные записи.

Функция `check_policy(action, object)` формирует код вида `READ:USERS` или `WRITE:PARAMETER` и проверяет наличие разрешения у текущего активного пользователя.

Таким образом, разрешение на операцию может зависеть одновременно от:

1. `GRANT EXECUTE`/`GRANT SELECT` на уровне PostgreSQL;
2. результата `check_policy()` внутри серверной функции.

## 4. Минимизация прямого доступа

В конце `01_schema.sql` выполняются:

```sql
REVOKE ALL ON ALL TABLES IN SCHEMA asu_schema FROM PUBLIC;
REVOKE ALL ON ALL SEQUENCES IN SCHEMA asu_schema FROM PUBLIC;
REVOKE ALL ON ALL FUNCTIONS IN SCHEMA asu_schema FROM PUBLIC;
```

Прямые права на базовые таблицы и последовательности также отзываются у прикладных ролей `app_*`. После этого им выдаются права только на необходимые представления и функции.

Например, оператор получает выполнение `f_get_current_params()`, `f_get_active_alarms()` и `f_confirm_alarm()`, но не получает прямой `SELECT` из `access_log` или `UPDATE` таблицы `control_objects`.

## 5. SECURITY DEFINER и search_path

Основные функции бизнес-логики выполняются как `SECURITY DEFINER` и фиксируют:

```sql
SET search_path = asu_schema, pg_temp
```

Это позволяет функции работать с базовыми таблицами от имени владельца функции, не выдавая вызывающему пользователю прямые права на эти таблицы. Фиксированный `search_path` также снижает риск обращения к одноименным объектам из посторонней схемы.

## 6. Разделение технологических данных

`control_objects` содержит признак:

```text
is_commercial_secret
```

Для минимального доступа используются `v_unprivileged` и `v_operator`, которые выбирают только активные объекты с `is_commercial_secret = FALSE`.

`v_engineer` и `v_privileged` содержат полный активный набор объектов, включая признак конфиденциальности.

В GUI ограниченные строки дополнительно визуально отмечаются для инженера и привилегированного пользователя.

## 7. Изменение технологического параметра

Из Python вызывается:

```text
privileged_ops.update_parameter()
        │
        ▼
sp_update_parameter(object_id, new_value)
```

Серверная функция:

1. проверяет `WRITE:PARAMETER`;
2. проверяет корректность идентификатора и значения;
3. получает старое значение, минимальную и максимальную границы;
4. обновляет `control_objects.current_value`;
5. записывает старое и новое значение в `access_log`;
6. если новое значение вышло за допустимые границы, создает активную запись в `alarm_log` с типом «Авария».

Внутреннее обновление маркируется параметром `asu.internal_update`, чтобы триггер аудита не создавал дублирующую запись для штатного изменения через функцию.

Одновременно существует `trg_audit_control_objects`: если `current_value` изменяется в обход штатной функции, триггер фиксирует это как отдельное событие.

## 8. Аварийные события

`f_get_active_alarms()` возвращает только записи со статусом `ACTIVE`.

`f_confirm_alarm()`:

- требует `CONFIRM:ALARM`;
- переводит запись в `CONFIRMED`;
- сохраняет `confirmed_by` и `confirmed_at`;
- пишет событие `CONFIRM_ALARM` в общий журнал.

## 9. Управление пользователями

Администратор ИС работает через функции БД, а не через прямое изменение таблицы `users`.

### Создание / обновление

`sp_add_user()`:

- проверяет `MANAGE:USERS`;
- нормализует и проверяет логин регулярным выражением;
- требует пароль длиной не менее 8 символов;
- сопоставляет прикладную роль с `app_*`;
- создает либо обновляет LOGIN-роль PostgreSQL `user_<login>`;
- отзывает старые прикладные групповые роли и назначает выбранную;
- синхронизирует состояние `LOGIN/NOLOGIN`;
- создает либо обновляет запись в `asu_schema.users`;
- журналирует административную операцию.

### Блокировка и разблокировка

`sp_delete_user()` исторически называется «delete», но физически пользователя не удаляет: он устанавливает `users.is_active = FALSE` и, если LOGIN-роль существует, переводит ее в `NOLOGIN`.

`sp_set_user_active()` при разблокировке возвращает `LOGIN`, при блокировке устанавливает `NOLOGIN` и синхронизирует прикладной флаг `is_active`.

### Смена пароля

`sp_change_user_password()` выполняет `ALTER USER` для соответствующей PostgreSQL LOGIN-роли и журналирует действие.

## 10. Защита последнего администратора ИС

В проекте реализованы две проверки:

- логика внутри функций блокировки;
- триггер `trg_protect_last_admin` на таблице `users`.

Если операция оставит систему без активного пользователя с ролью «Администратор ИС», изменение отклоняется.

## 11. Аудит

Основной журнал — `access_log`. Он может содержать:

- прикладной `user_id`;
- PostgreSQL-пользователя `db_user`;
- тип события;
- тип действия;
- связанный технологический объект;
- старое и новое значение;
- дату и время;
- IP-адрес клиента;
- признак успешности;
- описание и технический текст ошибки.

`log_access()` получает адрес через `inet_client_addr()`.

В справочнике `action_types` предусмотрены, в частности:

```text
LOGIN
LOGOUT
VIEW_OBJECT
UPDATE_VALUE
CONFIRM_ALARM
ADD_USER
BLOCK_USER
UNBLOCK_USER
UPDATE_USER
CHANGE_PASSWORD
READ_LOG
POLICY_DENY
ERROR
```

Администратор ИБ использует `f_get_logs()` для общего журнала и `f_get_login_log()` для входов/выходов.

## 12. Обработка ошибок

В Python слой `db_helpers.py` выполняет `rollback` при ошибке и преобразует техническое исключение в `AppDatabaseError` с нейтральным пользовательским сообщением.

Подробности ошибки выводятся в интерфейсе только:

- при `ASUTP_DEBUG=1`;
- либо для роли «Администратор ИБ».

В PostgreSQL функция `log_error()` записывает служебные ошибки в `access_log` с действием `ERROR`.

## 13. Параметризация SQL

Python-клиент передает пользовательские значения через параметры `psycopg2`:

```python
cur.execute(sql, params)
```

а не подставляет их в запрос простой конкатенацией строк.

В `sp_add_user()` динамический DDL PostgreSQL формируется с использованием `quote_ident()` и `quote_literal()`, а логин до этого проверяется регулярным выражением.

## 14. Границы демонстрации

Проект демонстрирует прикладную и серверную логику контроля доступа, но не моделирует полный промышленный контур. В частности, здесь нет:

- PLC/RTU и физических исполнительных устройств;
- OPC UA, Modbus и других промышленных протоколов;
- реальной сегментации технологической сети;
- промышленной отказоустойчивости и резервирования;
- сертифицированных средств защиты;
- серверного механизма блокировки после нескольких неверных паролей.

Предустановленные логины и пароли используются только для локальной демонстрации и опубликованы в репозитории намеренно.
