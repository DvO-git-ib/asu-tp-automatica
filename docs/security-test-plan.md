# План ручной проверки проекта

Документ предназначен для проверки уже развернутой БД и Python-клиента без изменения исходного кода.

## 1. Подготовка

Выполните в `asu_tp_db`:

```text
01_schema.sql
02_accounts.sql
```

Для наполненного стенда дополнительно выполните:

```text
03_demo_seed.sql
```

Затем можно выполнить `04_security_checks.sql`. Он проверяет наличие объектов, роли, внешние ключи и часть `GRANT/REVOKE`, но выполняется из административной сессии и поэтому **не заменяет** проверки под реальными LOGIN-ролями.

Демонстрационные данные входа находятся в `demo_creditions.txt`.

## 2. Проверка подключения Python

Из корня проекта:

```bash
python src/gui.py
```

Для диагностики соединения можно отдельно запустить:

```bash
python src/db_connection.py
```

По умолчанию ожидаются:

```text
host = localhost
port = 5432
database = asu_tp_db
```

Если сервер использует другие параметры, задайте `ASUTP_DB_HOST`, `ASUTP_DB_PORT` и/или `ASUTP_DB_NAME` перед запуском.

## 3. Проверка аутентификации

### 3.1. Корректный вход

Войти под `operator / pass123`.

Ожидание:

- соединение устанавливается;
- приложение определяет роль «Оператор»;
- открывается главное окно;
- в `access_log` появляется действие `LOGIN`.

### 3.2. Короткий и полный логин

Проверить два варианта:

```text
operator
user_operator
```

Оба должны приводить к соединению под PostgreSQL LOGIN `user_operator`.

### 3.3. Неверный пароль

Несколько раз указать неверный пароль.

Ожидание: GUI уменьшает оставшееся число попыток и после достижения `ASUTP_MAX_LOGIN_ATTEMPTS` закрывает окно входа. После нового запуска приложения счетчик начинается заново.

## 4. Проверка прямого доступа к таблицам

Под прикладными LOGIN-ролями выполнить, например:

```sql
SELECT * FROM asu_schema.users;
SELECT * FROM asu_schema.control_objects;
SELECT * FROM asu_schema.access_log;
```

Ожидание: прямой доступ запрещен там, где роль не имеет явного разрешения на таблицу. Основной рабочий доступ должен происходить через выданные функции/представления.

## 5. Непривилегированный пользователь

Вход:

```text
unprivileged / unpriv123
```

Проверить:

- вкладку общедоступных параметров;
- отсутствие рабочих вкладок изменения параметров, аварий и администрирования;
- отсутствие в выборке параметров, отмеченных `is_commercial_secret = TRUE`.

SQL-проверка:

```sql
SELECT * FROM asu_schema.f_get_public_params();
```

Попытка вызвать `f_get_all_params()` должна быть недоступна по `EXECUTE` либо не дать данных согласно политике.

## 6. Оператор

Вход:

```text
operator / pass123
```

Проверить:

- вкладку «Параметры»;
- вкладку «Аварии»;
- список активных аварий;
- подтверждение выбранной аварии.

После подтверждения:

- статус записи в `alarm_log` становится `CONFIRMED`;
- заполняются `confirmed_by` и `confirmed_at`;
- в `access_log` появляется `CONFIRM_ALARM`.

Оператор не должен иметь возможность выполнять `sp_update_parameter()`.

## 7. Инженер и привилегированный пользователь

Входы:

```text
engineer / pass123
privileged / priv123
```

Проверить:

- просмотр полного набора активных параметров;
- отображение признака «Коммерч. тайна»;
- изменение значения параметра;
- журнал изменений;
- историю выбранного параметра.

### 7.1. Значение внутри диапазона

Изменить параметр на значение между `min_limit` и `max_limit`.

Ожидание:

- `current_value` обновляется;
- появляется запись `UPDATE_VALUE`;
- в журнале присутствуют старое и новое значения.

### 7.2. Значение за границей

Установить значение меньше `min_limit` или больше `max_limit`.

Ожидание:

- значение обновляется;
- событие изменения имеет тип «Авария»;
- в `alarm_log` создается новая запись со статусом `ACTIVE`.

## 8. Администратор ИС

Вход:

```text
admin / admin123
```

### 8.1. Просмотр пользователей

Убедиться, что отображаются ФИО, логин, должность, роль, статус и дата создания.

### 8.2. Создание пользователя

Создать тестового пользователя с:

- латинским логином длиной 3–31 символ;
- паролем не короче 8 символов;
- существующей должностью;
- существующей ролью.

Ожидание:

- создается/обновляется строка в `users`;
- создается LOGIN-роль `user_<login>`;
- ей назначается соответствующая `app_*` роль.

### 8.3. Проверка валидации

Проверить:

- слишком короткий пароль;
- логин с недопустимыми символами;
- пустые обязательные поля.

Ожидание: операция отклоняется с безопасным сообщением.

### 8.4. Блокировка / разблокировка

Заблокировать созданного пользователя.

Проверить:

```sql
SELECT rolname, rolcanlogin
FROM pg_roles
WHERE rolname = 'user_<login>';
```

Ожидание после блокировки:

```text
users.is_active = false
rolcanlogin = false
```

После разблокировки:

```text
users.is_active = true
rolcanlogin = true
```

### 8.5. Смена пароля

Сменить пароль пользователя и проверить, что старый пароль больше не дает подключиться, а новый дает.

### 8.6. Последний администратор

Попытка оставить систему без активного администратора ИС должна быть отклонена. Проверка существует и в бизнес-функциях, и в триггере `trg_protect_last_admin`.

## 9. Администратор ИБ

Вход:

```text
ib_admin / ib123
```

Проверить:

- «Журнал операций»;
- «Входы/выходы»;
- просмотр пользователей;
- человекочитаемые названия типов событий и действий;
- IP-адрес клиента в строках, где PostgreSQL способен определить его;
- записи `READ_LOG`, возникающие при просмотре журналов.

## 10. Матрица доступа

Под любой ролью открыть вкладку «Матрица доступа».

Данные должны приходить из:

```sql
SELECT * FROM asu_schema.f_get_access_matrix();
```

Текущая роль выделяется в интерфейсе.

Для более глубокой проверки сравнить содержимое с `permissions` и `role_permissions` от административной сессии.

## 11. Аудит входа и выхода

1. Войти под несколькими ролями.
2. Использовать «Сменить пользователя» или закрыть приложение штатной кнопкой.
3. Войти как `ib_admin`.
4. Открыть журнал входов/выходов.

Ожидание: присутствуют `LOGIN` и `LOGOUT` с PostgreSQL-логином и временем события.

## 12. Ошибки и DEBUG_MODE

Обычному пользователю Python показывает нейтральный текст ошибки.

Для локальной диагностики можно перед запуском включить:

Windows PowerShell:

```powershell
$env:ASUTP_DEBUG = "1"
python src\gui.py
```

Linux:

```bash
export ASUTP_DEBUG=1
python src/gui.py
```

При этом техническое описание ошибки дополнительно выводится в консоль/интерфейс в соответствии с логикой приложения.

## 13. Проверка `04_security_checks.sql`

Скрипт должен показать:

- базовые таблицы схемы;
- отсутствие старых служебных таблиц `backup_log` и `error_log`;
- количество записей;
- прикладных пользователей;
- шесть PostgreSQL LOGIN-ролей;
- матрицу прав;
- внешние ключи;
- отсутствие прямых `SELECT` у выбранных пользователей;
- выполнение основных функций от владельца БД;
- соответствие ключевых EXECUTE-привилегий ожидаемым значениям.

Если `matches_expected = true`, проверенный `GRANT EXECUTE` соответствует ожидаемой конфигурации.
